`pnpm outdated` でメジャーバージョンが異なっているライブラリのうち、1つだけを最新の安定版に上げてください。

## 対象ライブラリ

`$ARGUMENTS` にライブラリ名が指定されている場合はそれを対象にしてください。
指定がない場合は以下の手順で候補を洗い出し、ユーザーに確認してください。

## 手順

1. `pnpm outdated` を実行する
2. Current と Latest でメジャーバージョン（semver の先頭の数字）が異なるものだけを抽出する
   - 例: `25.9.4 → 26.1.1` は対象、`16.2.4 → 16.2.10` や `0.34.5 → 0.35.3` は対象外
3. 対象が複数ある場合は、それぞれについて `npm view <package> versions --json` や `npm view <package> dist-tags --json` で候補バージョンを調べ、AskUserQuestion でユーザーにどのライブラリを1つ上げるか選んでもらう
   - 対象が1つしかない場合でも、確認なしに進めず一度ユーザーに提案する
4. 選ばれたライブラリについて「安定していて一番新しいバージョン」を選ぶ
   - `beta` / `rc` / `dev` / `next` などのプレリリースタグが付いたバージョンは除外する
   - npm の `latest` dist-tag が指しているバージョンでも、それが直近のメジャーを1つ以上飛ばす大きな破壊的変更（例: ネイティブ実装への移行など）を含む場合は、その旨をユーザーに伝えて本当にそれで良いか確認する
   - **他のライブラリはメジャーバージョンを上げない**（今回のスコープはあくまで1ライブラリのみ）
5. `pnpm add -D <package>@<version>`（devDependencies の場合）または `pnpm add <package>@<version>`（dependencies の場合）で更新する
6. `pnpm install` によって `pnpm-lock.yaml` のフォーマットが崩れることがあるため、`npx prettier --write pnpm-lock.yaml` を実行する
7. `npm run lint` と `npm run build` を実行し、型エラー・lintエラー・ビルドエラーが出ないことを確認する
   - エラーが出た場合は原因を調査し、対応方針をユーザーに確認してから修正する
8. 変更内容（Before/After のバージョン、選定理由、検証結果）を簡潔にまとめて報告する

## 注意事項

- コミットは明示的に依頼されない限り行わない
- 複数ライブラリを一度に上げない（ユーザーから明示的に依頼された場合を除く）
- 迷ったら「安定版」を優先し、プレリリース版やリリース直後で情報の少ないバージョンは避ける
